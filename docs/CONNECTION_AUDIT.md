# 客户端与服务端连接及管理能力审核

审核日期：2026-10-15。对象：当前工作区源码。

**后续修复状态（0.2.0，2026-10-15）：下文四项问题已修复，并新增客户端服务端管理页。管理员可查看 / 创建 / 启停用户、修改并持久化数据保留天数；成员可生成自己的上传密钥并自动接入。96 项自动化测试通过。下文保留最初审核发现作为历史记录，新的发布验证见 `docs/VALIDATION.md`。**

用户确认尚未部署，本次以源码和本机真实 HTTP 联调为准；“客户端设置服务端”的范围包括连接设置、用户管理和服务端运行参数管理。

## 结论

**当前客户端与服务端可以正常交换应用使用记录和设备状态，基本通信协议一致，断线补传、确认后标记、重试去重和连接间缓存隔离均通过本机验证。但仍有四项已复现的问题或验证缺口；客户端内管理服务端用户和运行参数尚未实现。**

现有的“服务器地址设置”只决定客户端连接到哪里，不会修改服务器的监听端口、用户或数据保留策略。客户端的“打开服务器”会打开系统浏览器，也不等同于客户端内管理。

本次产出为审核报告与隔离验证脚本，以下问题尚未修复。

## 已复现的问题及改进点

### 1. [P2] 验证期间修改设置，界面与实际保存内容不一致

位置：`client/focus_agent/gui.py:1070–1140`。

复现：填写服务器 A，点击保存；在网络验证结束前，把地址改成服务器 B。程序验证并保存之前截取的 A，但地址输入框仍显示 B，未保存标记也被清除。

影响：用户看到 B 和“设置已保存”，实际上传仍使用 A。密钥、端口、设备名称等验证期间的修改也有同样的风险。它不是已经验证连接之间的自动串传，但会让用户误判当前数据目的地。

原因：验证时保存了 `job_candidate`，只禁用了保存 / 测试按钮；其他输入框仍可编辑，保存完成后又统一调用 `set_dirty(False)`。

建议：验证期间锁定相关输入，或为设置维护修改版本；验证返回时若表单已变化，只保存被验证的版本，并保留新修改的未保存标记。

### 2. [P2] 切回原账户会再次生成设备 ID，同一电脑出现多个设备

位置：`client/focus_agent/gui.py:1112–1114`。

复现：账户 A → 账户 B → 账户 A。回到 A 时，连接归属恢复为原来的 `destination`，但 `device_id` 与最初的 A 不同；原缓存仍携带旧设备 ID，新记录将携带新设备 ID。

影响：旧缓存能够补传，也不会因此发给 B；但服务端会把同一电脑拆成不同设备，时间线和设备统计分散。反复切换服务器也有相同机制。

建议：按“服务器与账户”保存稳定的设备 ID 映射，回到已使用过的连接时复用原身份。不同账户仍应使用不同身份。

### 3. [P2] 应用记录的冲突检查遗漏开始时间和持续时间

位置：`server/app/main.py:406–411`。

复现：先上传一条 30 秒的使用记录，再用相同事件 ID、应用名、进程名和结束时间，把开始时间提前，改成 60 秒。服务端仍返回成功和 `duplicates=1`，确认该 ID，数据库继续保留原来的 30 秒。

影响：同 ID、不同内容的使用记录会被误判为完全相同的重试。若出现缓存修复、客户端缺陷或其他平台接入错误，客户端会认为新内容已确认，数据差异被静默掩盖。正常客户端生成不可变事件时不容易触发。

建议：补齐开始时间和持续时间的一致性校验，内容冲突返回 409；同时兼容保留期导致服务端截断记录的情况。也可以保存原始规范化事件摘要用于一致性判断。

### 4. [P2，验证缺口] “测试连接成功”不代表上传可用

位置：`client/focus_agent/network.py:66–73`。

复现：让本机测试服务正常响应 `GET /api/v1/agent/check`，单独对上传地址返回 403。客户端连接测试成功，实际上传失败。

影响：反向代理只放行 GET、上传路径配置错误或设备身份已归属另一账户时，单纯测试密钥可能通过，但数据仍无法上传。这不影响本次正常路径的上传结果，属于连接诊断覆盖不足。

建议：界面区分“地址与密钥验证成功”“设备上传验证成功”“最近一批已入库”。可增加明确的上传诊断操作，使用空批次验证 POST 和设备归属，并说明这会登记 / 更新设备心跳；仅检查 GET 的操作应准确标注验证范围。

### 建议的实现范围和顺序

1. **先修复上述数据一致性与设置状态问题。** 同时把已复现问题转换为期望正确行为的回归测试。
2. **增加客户端“服务端管理”页。** 管理员登录后查看用户列表、新建账户、启用 / 停用账户；普通账户只能处理自己的密码、密钥等事项。上传密钥继续只用于设备上传，不能因添加管理功能而获得管理员权限。
3. **先开放应用可管理的运行参数。** 第一项可以是数据保留天数，限定 1–365 天，保存后持久化；清理任务和所有展示查询使用同一份有效值。缩短保留期会删除历史数据，界面需要展示这一影响。
4. **将部署参数明确展示。** 对外端口、绑定地址、镜像、证书可先提供只读信息和配置导出。若要求客户端直接修改并重启 Docker，需单独设计部署侧权限、凭据、执行方式及重连机制；当前服务端没有这类能力。

管理接口宜返回明确的成功 / 失败、当前生效值、管理员权限与服务端支持能力，方便客户端判断保存是否真正生效。可以复用现有网页登录会话及 CSRF 规则，也可以新增独立的管理会话；不应把网页登录密码简单拼进现有上传请求。
